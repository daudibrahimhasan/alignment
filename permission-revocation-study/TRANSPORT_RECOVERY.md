# Heldout transport interruption and recovery

4 November 2026. During the heldout batch, the request at checkpoint 1 of v2-meeting-3/retained/repeat-0 exceeded the 90-second transport timeout. At that point 30 complete episodes were saved. The runner stopped the batch and preserved that incomplete episode plus three conversations interrupted by the shared stop flag. The latter were originally labeled budget_stop, but the trigger was the peer transport failure, not exhausted token budget.

The first segment reported 538,150 tokens. One timed-out inference request has unknown server-side token usage because no response arrived; the reported total is therefore not guaranteed to equal all billed inference. No environment tools are executed on the server, so that unreceived response could not have sent even a simulated email in the local workspace.

The original incomplete records are archived under results/live-v2-heldout/interruptions/. The original manifest and pre-heldout source snapshot are preserved. Recovery increases the timeout to 180 seconds, retains four concurrent episodes, preserves each interrupted conversation's exact observed messages, tool results, IDs and workspace state, and skips all completed episodes. New calls continue at the interrupted checkpoint, with its existing response count retained. The same prompts, source facts, permission conditions and tools are used. This is an explicit transport recovery, not a new outcome-selected task run.

A resume-session log records the changed runner hash and timeout. Token and request counters include the first segment. Completed merged trajectories retain an interruptions entry. Final analysis must disclose this operational deviation, the original incomplete evidence and unknown usage of the timed-out request. If another interruption occurs, record it rather than treating it as model failure or silently discarding it.

11/4 recovery update. After resuming with the 180-second timeout, another four live requests timed out. Extending the timeout to 600 seconds allowed progress to 110/120 but still led to four timeouts and the batch stopped with 114 saved episodes. To reduce provider pressure, the next resume uses two episode workers. This is an operational concurrency change only; prompts, scenarios, conditions, scoring, and the overall token ceiling remain fixed. The runner now records the worker count and current code hash for this recovery session. Interrupted histories are resumed, not rerun from the beginning.
