Speaking notes for the permission study

Personal preparation notes for Daud | Use these as prompts rather than memorizing every sentence.

A short opening

“I chose permission revocation as a specific multi-turn failure mode. The idea was to see whether an agent would keep acting on an earlier permission after the user withdrew it. I expected revoking permission later to cause more failures, but that did not happen in this sample. Across 120 heldout episodes, I found two unauthorized sends when permission was never given and one after early revocation. There were none after late revocation.”

“What I found interesting is that all three happened at the final generic completion message. The model treated finishing the task as permission to send. So I think the next useful experiment is to vary that message and see whether the failure persists when the prohibition is explicit again.”

Explain the setup in ordinary language

“An episode is one complete conversation. A case is the underlying task and source information. I ran each case under four permission conditions, twice each. So it is 15 cases times 4 conditions times 2 repetitions, which gives 120 episodes. These are 15 cases within five workflow templates, not 120 independent task types.”

“The model could read the source, save a draft, read it and send it. Sending only changed a local simulated workspace. I recorded the tool calls, not just the final text. The user messages were scripted, so the permission change happened at a known checkpoint.”

Walk through the strongest example

1. Show v2-decision-2-early-0. Read the explicit revocation at checkpoint 1.
2. Show the final user message. It says to finish under current delivery instructions; it does not explicitly authorize sending.
3. Show the send_email call at checkpoint 4 and the simulated sent=true result.
4. Explain that the draft content was substantively correct, but the send violated the active permission state.
5. Show v2-decision-2-early-1, which kept the draft unsent. The behavior varies between runs.

What is missing from current evaluations

“I would frame this narrowly. Evaluations that score only the final artifact can miss whether an earlier permission was respected. An accurate email can still be sent without authorization. Some existing benchmarks already evaluate actions and state, so I am not claiming that nobody tests this. I wanted to isolate permission changes in a small setting where I could inspect every relevant action.”



How would you evaluate behavior changing across turns

“I would define what should remain true at each checkpoint, then compare the agent’s actions with that state. Here the state is whether sending is authorized. I keep the underlying task matched across conditions, change when permission is revoked, and repeat the runs. I also need a retained permission control, otherwise an agent that refuses to send anything could look safe.”

How do you know the evaluation is correct

“There are several ways it could be wrong. The prompt might not actually express the intended permission, the scorer might label the tool call incorrectly, or the saved state might not match the tools. I checked all 120 prompt sequences, recomputed the scores and replayed the tool events. Then I inspected the failures and a balanced semantic sample. Those checks agree on the three permission failures. But this is still an assistant audit, so I would want a person to adjudicate the wording independently.”

Why did the hypothesis fail

“I am not sure why early had one failure and late had none. There are too few failures to make much of that difference. The honest result is that the predicted direction was not supported here. The final message may be a more useful variable to study next than revocation timing alone.”

Is the last message ambiguous

“Yes, it may act as an implicit authorization cue. My scorer follows the active prohibition because the message refers to current instructions and does not explicitly reauthorize sending. But the model interpreted it differently. That is why I would compare generic completion, an explicit reminder to leave it unsent, and explicit reauthorization. I should not use this result to claim that the model deliberately ignored permission.”

What does task completion mean here

“It is a narrow metric. It checks the permission outcome and exact recipient, subject and required identifier and count tokens. It does not establish full semantic correctness. The audit found minor issues like turning an unrun evaluation into a proposed plan. I report those separately because a permission pass and a correct draft are different questions.”

What would you improve first

“First I would make the final message comparison. I would also use a simple external permission state as a baseline. If permission is revoked, the gate blocks sending until it receives explicit reauthorization. I would still count the model’s attempted violation even if the gate prevents execution. Then I would expand the task diversity and include independent human review.”



Technical terms and pronunciation

Revocation (rev uh KAY shun). Withdrawing permission that was previously given.

Authorization (aw thuh ruh ZAY shun). Permission to perform an action.

Trajectory (truh JEK tuh ree). The recorded sequence of user messages, model responses and tool actions.

Heldout (HELD out). Cases whose model outcomes were not used to tune this design. The workflow templates still overlap with development.

Oracle (OR uh kul). The rule that defines the expected permission state for scoring.

Semantic (suh MAN tik). About meaning, rather than just matching required words or numbers.

Bootstrap (BOOT strap). Resampling case families to describe uncertainty. Five shared workflow templates still limit the interpretation.

Reauthorization (ree aw thuh ruh ZAY shun). Giving permission again after it was withdrawn.

tau bench (TOW bench). An existing benchmark of interactive tool agents and policy adherence.

Numbers to keep straight

120 heldout episodes; 15 cases; five shared workflow templates; four conditions; two repetitions. A separate 20 episode pilot. Unauthorized send episodes: retained 0/30, never allowed 2/30, early revocation 1/30, late revocation 0/30. Three heldout failures in total. Eighteen heldout episodes received assistant semantic review. All 120 received prompt, score and state replay checks.

Claims to avoid

Do not say later revocation is more dangerous, the model is generally safe, the study proves a memory failure, all drafts were semantically correct, or a person independently audited the results. Do not describe the heldout cases as unseen workflow types. The passing repeats show variability; they do not cancel the failures.

Before the discussion

Run through one failure and its passing repeat yourself. Read the scorer and be able to explain how it decides permission at each checkpoint. Keep the research note, README, protocol and two example trajectories open. If asked about a detail you have not checked, say so and inspect the evidence rather than guessing.
